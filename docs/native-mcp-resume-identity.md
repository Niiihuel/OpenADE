# Identidad MCP para reanudar un turno nativo

El runner congela el catálogo de herramientas y, cuando puede verificar **todos** los servidores MCP habilitados, persiste `McpRuntimeCommitted` antes del primer pedido al modelo. El evento guarda una versión y un SHA-256; no guarda rutas, variables ni credenciales. Replay acepta un solo marcador, después de `ToolCatalogCommitted` y antes de `ModelContextCommitted`, y falla ante versión, formato u orden inválidos. La recuperación descubre de nuevo los servidores y compara el digest antes de volver a pedir un permiso o ejecutar una llamada `ToolReady`.

## Servidores que pueden generar el marcador

- **stdio sin credenciales:** exige ejecutable absoluto y canónico de formato binario directo. Incluye contenido del ejecutable y archivos declarados por argumentos, argv exacto, directorio, entorno mínimo de arranque, configuración, `serverInfo` y catálogo. Comprueba ejecutable y argumentos antes y después del arranque. Rechaza intérpretes, lanzadores de paquetes, código indirecto y cualquier variable o argumento que pueda portar credenciales. Los archivos tienen límite de 64 MiB.
- **HTTP 2026-07-28 moderno sobre HTTPS remoto:** exige conexión TLS validada por el cliente HTTP, URL canónica sin usuario, query ni fragmento, `server/discover` con nombre y versión, `tools/list` completo y catálogo todavía vigente. Incluye endpoint, identidad y límites del cliente, `serverInfo` y digest del catálogo congelado. La huella combinada ordena servidores por ID y etiqueta cada transporte. Si todos los servidores son stdio, conserva exactamente el digest anterior.
- **HTTP con bearer estático en Windows:** agrega una HMAC-SHA-256 del token con clave aleatoria de 256 bits guardada como credencial del usuario en Windows Credential Manager. El journal sólo recibe el digest combinado; ni token ni clave salen del almacén/cliente. Al reiniciar se vuelve a resolver la variable de entorno y se recalcula la HMAC. Un token o clave distinta cambia el marcador y bloquea la llamada pendiente. Si el vault falla, no hay identidad de recuperación para ese servidor.
- **HTTP con OAuth en Windows:** una autorización nueva guarda una revisión aleatoria dentro de la misma credencial que los tokens. La revisión se liga a resource, issuer, client ID, scopes y metadatos del servidor de autorización. Una renovación compara atómicamente los tokens anteriores bajo un mutex entre procesos y conserva la revisión sólo si siguen siendo los mismos; una reautorización la rota. En reconexión se redescubre el servidor OAuth, se renueva el token si hace falta y se compara la revisión antes de certificar el marcador. El cliente comprueba de nuevo esa revisión antes de cada `tools/call`. Un cambio detectado antes del POST produce `AuthorizationChanged`, sin declarar incierto un efecto que todavía no empezó.

`McpHttpClient::resume_server_identity(id)` sólo devuelve identidad **después** de `list_tools` y mientras el cliente está abierto y su catálogo no fue invalidado. `mcp_runtime_digest` combina `McpServerRuntimeIdentity::{Stdio,Http}` con el digest del catálogo compuesto. Si falta la identidad de un solo servidor habilitado, el host debe pasar `None` al runner: no hay marcador parcial.

## Casos que siguen bloqueados

HTTP loopback, HTTP legacy con sesión y credenciales opacas sin prueba de revisión siguen sin generar identidad durable. En plataformas sin almacén seguro de clave para bearer, ese tipo de servidor falla cerrado. `MemoryTokenStore` sólo permite identidad dentro del mismo proceso y no prueba persistencia tras reinicio. Las credenciales OAuth anteriores a la revisión nueva se pueden usar en vivo, pero no habilitan resume hasta completar otra autorización. El protocolo no expone una prueba de cuenta o despliegue: un proveedor que cambie en silencio el significado de un mismo grant sigue fuera de lo verificable por el cliente.

Una reconexión de HTTP legacy después de `SessionExpired` invalida el catálogo anterior; la llamada que ya se despachó queda `EffectUncertain` y no se repite. Una notificación `tools/list_changed`, una nueva lista distinta o una sesión reemplazada invalidan el catálogo de forma sticky. Una llamada `ToolOutcomeUncertain` exige verificación manual aun cuando la huella coincida: reejecutarla podría duplicar efectos. Un HTTP 401, corte de red o timeout después de despachar `tools/call` tampoco se repite automáticamente, aun si una renovación posterior conserva la revisión OAuth.

La autoridad TLS y el catálogo no demuestran que un servicio remoto conserve exactamente el mismo código o estado entre turnos. Un despliegue nuevo que anuncie la misma versión y las mismas herramientas puede pasar esta comprobación. La revisión OAuth prueba continuidad de la credencial local, no que el servidor mantenga la misma cuenta, permisos o semántica; un cambio de scopes sí invalida el digest. La huella de stdio tampoco cubre bibliotecas dinámicas, datos externos ni dependencias no declaradas.

## Cierre de una sesión HTTP legacy parcialmente inicializada

El cliente asume la propiedad de un `Mcp-Session-Id` válido al recibir los headers de `initialize`, antes de leer o validar su cuerpo. Si falla la respuesta, la versión negociada o `notifications/initialized`, intenta `DELETE` del mismo endpoint y sesión antes de devolver el error. La limpieza usa un token independiente de la cancelación del handshake y un plazo nuevo de `request_timeout` que incluye autorización y envío HTTP. Antes de una negociación válida usa la versión ofrecida en `initialize`; después usa la versión negociada, conservando las mismas comprobaciones de credencial y endpoint.

Una sesión parcial nunca se entrega como cliente utilizable. Un reemplazo fallido después de `SessionExpired` también cierra el cliente local; no permite descubrir herramientas ni despachar llamadas nuevas. Cuando la limpieza termina, se conserva la clase original (`Cancelled`, `Timeout` o error de protocolo). Si falla, `HandshakeCleanupFailed` conserva la causa original como source y una segunda causa de limpieza, e indica que la sesión remota puede seguir activa. Si el reemplazo empezó después de despachar una herramienta, el resultado sigue `EffectUncertain` y su diagnóstico incluye ambos fallos, sin repetir `tools/call`.

Un `DELETE` exitoso o un 404 permite descartar el ID local; un 405 también libera la propiedad local siguiendo el contrato anterior de servidores sin terminación explícita, pero no confirma que el servidor haya eliminado su sesión. Un fallo de red, autorización, HTTP o timeout no confirma la liberación remota. No hay almacenamiento durable de IDs de sesión legacy ni recuperación de sesiones remotas tras reiniciar. Si el servidor asignó una sesión antes de entregar headers válidos, o devuelve un ID rechazado por las comprobaciones de tamaño/formato, el cliente no tiene un identificador seguro para eliminarla.

El runtime HTTP mantiene vivo el futuro de conexión durante la cancelación cooperativa, espera su intento de limpieza y conserva los errores de cierre de clientes iniciados anteriormente. La preparación distingue una cancelación simple de una cancelación con cierre fallido, que se presenta como diagnóstico de runtime. Abandonar arbitrariamente el futuro (`Drop`), apagar su runtime Tokio o terminar el proceso puede impedir el cierre async; estas pruebas no garantizan limpieza después de esas fronteras ni prueban el estado interno de un servidor externo.

Las pruebas HTTP locales `failed_legacy_initialized_closes_owned_session_before_returning`, `cancelled_legacy_initialized_still_waits_for_session_delete` y `timed_out_legacy_initialized_still_waits_for_session_delete` verifican ID, versión, credencial y espera de respuesta DELETE. `failed_legacy_handshake_reports_delete_failure_without_losing_cause` y `cancelled_legacy_handshake_reports_bounded_delete_timeout` verifican las dos causas y el plazo independiente. `malformed_legacy_initialize_still_closes_allocated_session` cubre JSON inválido, estructura incompleta y versión rechazada después de recibir un ID. Las pruebas de reemplazo verifican revocación del cliente, cierre no duplicado tras respuesta válida y una sola llamada de herramienta aun cuando fallan reinicialización y DELETE. `runtime_cancellation_during_legacy_initialize_waits_for_partial_session_delete` ejerce la preparación desktop real, cancelación y DELETE 204/503; no admite un turno ni ejecuta inferencia.

## Referencia Codex y pruebas

En `references/codex/codex-rs/core/src/session/mcp.rs`, Codex refresca configuración y autenticación del runtime MCP al cambiar pasos o credenciales. `references/codex/codex-rs/rmcp-client/src/http_client_adapter.rs` maneja la sesión HTTP y la reconexión. Ese mecanismo no es una prueba durable de que una llamada remota pendiente pueda repetirse; OpenIDE exige el marcador de identidad y el estado anterior al efecto antes de hacerlo.

Las pruebas `mcp_identity` cubren launcher/archivos, orden e identidad mixta, cambios de endpoint, `serverInfo`, catálogo y autorización reconstruida. Las pruebas `mcp_http` usan un servidor HTTP local para rotación de bearer entre conexiones, reconexión/expiración legacy, cambio explícito de lista y prohibición de repetir un `tools/call` incierto. Las pruebas OAuth cubren renovación del mismo grant, reautorización, cambio de scopes y rechazo anterior al POST. Los tests positivos de la puerta HTTPS ejercitan el estado del cliente con una autoridad simulada; no sustituyen una prueba de integración con un servidor HTTPS real o con un servidor OAuth de producción.
